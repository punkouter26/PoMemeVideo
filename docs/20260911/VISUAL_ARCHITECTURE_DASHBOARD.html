Tier 1 · The thirty-second read

One host, seven slices, five tables

A single deployable ASP.NET Core process serves the API, the SignalR hub and the Blazor WebAssembly client. Inside it, code is grouped by feature slice rather than technical layer, and the rule that keeps that arrangement honest is enforced by discipline in exactly two files.

Tier 2 · Topology and dependency rules

Deployment topology

The dependency rule, and the two places it lives

Slice autonomy is not enforced by the compiler — every slice type is public in the same assembly. It is enforced by two conventions:

// Api/GlobalUsings.cs — the entire file
// Infrastructure and the shared kernel are globally visible. Feature slices are NOT:
// a slice reaches a sibling only through PoMemeVideo.Shared.Contracts, resolved via DI.
// The composition root (Configuration/) imports concrete slice types explicitly.
global using PoMemeVideo.Api.Common;
global using PoMemeVideo.Shared;
global using PoMemeVideo.Shared.Contracts;
global using PoMemeVideo.Shared.Domain;

GlobalUsings.cs:1-7

Adding a single global using PoMemeVideo.Api.Features.* line here re-opens cross-slice coupling everywhere at once, silently. The second convention is that Configuration/ is the composition root and imports each concrete slice namespace explicitly, per file ServiceRegistrationExtensions.cs:10-17EndpointMappingExtensions.cs:4-11.

One place the rule bends

MemeLibraryEndpoints calls SeedSoundsCommand, which lives in its own slice, and its comment says “Sibling slice Admin hosts the seeding logic…” MemeLibraryEndpoints.cs:107-110. There is no Admin slice in the tree — SeedSoundsCommand.cs sits in Features/MemeLibrary/, so the call is intra-slice and legal; only the comment is stale. Separately, OutputEndpoints injects the concrete BlobStorageService rather than IBlobStorageService on four routes OutputEndpoints.cs:83,120,156,192, which works because both are registered, but bypasses the contract the rule is built on.
