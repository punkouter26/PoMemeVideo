Tier 1 · The thirty-second read

Deny by default, with four ways in

Authorization fails closed: a FallbackPolicy requiring an authenticated user applies to every endpoint that does not explicitly opt out. Authentication is a back-end-for-front-end — the WASM client never holds a token, only an encrypted HttpOnly cookie. Four schemes can mint that identity, and three of them are environment-gated.

Three findings

1 · The challenge redirects to a route that does not existHigh

options.LoginPath = "/login" sits inside the else branch taken only when AzureAd:ClientId is blank ServiceRegistrationExtensions.cs:166-180. With Entra ID configured, AddMicrosoftIdentityWebApp registers its own cookie scheme and nothing sets LoginPath, so the framework default applies. Observed against the built app under ASPNETCORE_ENVIRONMENT=Staging with AzureAd:ClientId present from Key Vault:

$ curl -i http://localhost:5399/api/ingestion/sessions
HTTP/1.1 302 Found
Location: http://localhost:5399/Account/Login?ReturnUrl=%2Fapi%2Fingestion%2Fsessions
Content-Length: 0

$ curl -o /dev/null -w '%{http_code}' http://localhost:5399/Account/Login
404

An unauthenticated XHR therefore receives a 302 to a dead path instead of a 401, and a browser follows it to a 404. This is also why the API E2E suite explicitly declines to assert the posture: “Deny-by-default is deliberately NOT asserted here” RoutingContractApiTests.cs:200-204.

2 · Header-asserted identity is live in Staging, not just Development and TestHigh

FakeAuthHandler authenticates a caller from the unverified X-Fake-User header, and both its registration ServiceRegistrationExtensions.cs:187-191 and the middleware that promotes it EndpointMappingExtensions.cs:70-83 are guarded by !IsProduction() — which is true of Staging, and of any custom environment name. Observed under Staging:

$ curl -H 'X-Fake-User: docs-probe' \
       http://localhost:5399/api/ingestion/sessions/1111…1111
{"error":"SESSION_NOT_FOUND","sessionId":"11111111-1111-1111-1111-111111111111"}

The request reached the protected handler; without the header the same URL returned the 302 above. The class’s own guardrail — a constructor that throws in Production FakeAuthHandler.cs:29-34 — is exactly right, but IsProduction() is a narrower gate than the “dev/test only” intent the comments state. The user id is MD5(userName), so any caller can deterministically assume any other fake user’s partition FakeAuthHandler.cs:72-77.

3 · Two anonymous endpoints do more than report statusMedium

POST /api/memelibrary/seed is AllowAnonymous MemeLibraryEndpoints.cs:145 and performs unauthenticated writes: it reads a manifest from disk, downloads any missing clip from its sourceUrl over the network, uploads to Blob Storage, upserts rows into SoundAssets, and evicts the shared cache. Observed under Staging: an unauthenticated POST returned 200. GET /diag is also anonymous DiagEndpoint.cs:81 and, while every value is masked, the masking is first three + last three characters for anything longer than six DiagEndpoint.cs:150-154 — so an anonymous caller learns which of 15 named secrets exist, plus six characters of each, including AzureAd:ClientSecret and AiFoundry:Key. Short values such as TenantId="common" render as ***.

Tier 3 · Claims, policies and refusal codes

Token formats, claims and exact payloads

There is no token format on the wire

This is a BFF. The browser holds one Data-Protection-encrypted cookie and nothing else; the client’s own auth provider says so: “The WASM client never sees a token — it only learns whether the HttpOnly session cookie maps to a signed-in user” ApiAuthenticationStateProvider.cs:7-11. The OIDC id-token is consumed server-side in OnTokenValidated and never forwarded. No AddJwtBearer, no [Authorize(AuthenticationSchemes=…)], no downstream API token acquisition appears in the solution.

How a caller becomes a UserId

public static UserId? TryGetUserId(HttpContext httpContext)
{
    var user = httpContext.User;

    // Cookie-based GUEST/ANON identities set NameIdentifier to a Guid directly.
    var nameId = user.FindFirstValue(ClaimTypes.NameIdentifier);
    if (Guid.TryParse(nameId, out var userId))
        return new UserId(userId);

    // Entra ID (OIDC) users: NameIdentifier is the `sub` pairwise id (not a Guid),
    // so fall back to the object-identifier (`oid`) claim, which is a stable Guid.
    var oid = user.FindFirstValue(EntraObjectIdSchemaClaim) ?? user.FindFirstValue("oid");
    return Guid.TryParse(oid, out var objectId) ? new UserId(objectId) : null;
}

The exact 401 / 403 payloads

RFC 9457

No 401 or 403 in this application emits an RFC 9457 application/problem+json body. The only problem-shaped payload in the codebase is GlobalExceptionHandler’s, it covers unhandled exceptions only, and it emits RFC 7231 type URIs plus two non-standard members GlobalExceptionHandler.cs:40-71. What follows is what the wire actually carries, captured from the built application under ASPNETCORE_ENVIRONMENT=Staging at commit a495207.

Unauthenticated call to a protected endpoint — no 401 at all

GET /api/ingestion/sessions

HTTP/1.1 302 Found
Location: http://localhost:5399/Account/Login?ReturnUrl=%2Fapi%2Fingestion%2Fsessions
Content-Length: 0
Server: Kestrel

(empty body)

Identical shape for POST /api/processing/sessions/{id}/initiate and GET /api/memelibrary/sounds. The cookie handler converts the authorization failure into a challenge; no status code in the 4xx range is ever sent.

The one genuine 401 — the API-docs gate

GET /scalar/

HTTP/1.1 401 Unauthorized
Transfer-Encoding: chunked
(no Content-Type)

Unauthorized — sign in to access API documentation.

Plain text, written by a bespoke middleware rather than the auth stack EndpointMappingExtensions.cs:52-66. Note it is written before UseAuthorization and after UseAuthentication, so it reads context.User directly.

403 Forbidden

Nothing in the application produces one. There is no authorization requirement an authenticated user can fail: no roles, no named policies, no resource-based handler. Ownership violations are deliberately rendered as 404, not 403 — GetByIdAsync returns null when OwnerUserId does not match VideoSessionTableRepository.cs:63-66, and the mutating paths throw SessionNotFoundException for the same case VideoSessionTableRepository.cs:160-168. A non-owner and a non-existent session are indistinguishable to the caller, which is the correct choice for an enumerable GUID key.

Secret handling

Secrets reach the process only through Key Vault or environment configuration. appsettings.json ships every secret slot as an empty string appsettings.json:14-45, and appsettings.Development.json is gitignored. The prefix manager loads PoMemeVideo--* with the prefix stripped, loads un-prefixed shared secrets as-is, and skips any secret belonging to a different Po* app Program.cs:84-95. The only place a secret value is ever rendered is /diag, masked (see finding 3). No secret value appears anywhere in this document set — key names only.
